# 安全模型

这个扩展给了桌宠执行脚本的能力。这个文档说清楚它拦得住什么、拦不住什么。

## 权限开关在谁手里

**在配置文件的作者手里，不在模型手里。**

`script_run` 的参数只有三个：`alias`、`command`、`args`。**没有 mode 字段**。

模型没办法把自己从 whitelist 提到 open。改模式要改 `config.json`，那需要文件写权限——模型只有这个扩展给的四个工具，没有 `write_file`。

⚠️ 但如果你的部署里同时装了带文件写入能力的 World，这个隔离就不成立了。这种情况请只用 whitelist 模式，并且白名单里不要放能改配置的脚本。

## whitelist 模式拦什么

### 路径穿越

```typescript
function insideRoot(target, root) {
  const t = resolve(target);
  const r = resolve(root);
  return t === r || t.startsWith(r + sep);
}
```

`../../../windows/system32/cmd.exe` 这种，resolve 之后落在根外，直接拒绝。

已测：`<allowRoot>/../Windows/cmd.exe` → 拒绝。

### 参数篡改

白名单条目的 `args` 是配置文件写死的，模型只能传 `alias`。它没法给 `rm -rf` 加参数。

### 输出爆炸

`maxOutputChars` 默认 4000。一个打印十万行的脚本不会把上下文冲掉。

已测：20000 字符输出被截到 4020。

### 无限挂起

`timeoutMs` 默认 60 秒，超时 `SIGKILL`。

已测：把超时改成 1 毫秒，脚本立刻被杀。

## whitelist 模式拦不住什么

**白名单脚本本身的权限。** 它跑起来之后能干白名单脚本能干的所有事——读文件、发请求、删东西。扩展管不了这一层。

所以白名单里放什么，是这个扩展安全性的**真正上限**。建议：

- 只放**单一用途**的窄脚本（启停服务、查状态、转换一个文件）
- 不要放「通用执行器」「万能工具箱」这类东西
- 不要放接收文件路径参数、然后对那个路径做删除或移动的脚本

## open 模式

接受任意 `command` + `args`，但：

- 拒绝 shell 元字符：`; & | > < \` $` 和换行
- 仍然有超时和输出截断

**这挡得住拼接注入，挡不住命令本身干坏事。**

`rm -rf /` 里没有元字符，照样会跑。所以 open 模式本质上等于「把执行权交出去」。

建议只在两种场景用：

1. 你自己盯着，让它做一件你明确指定的事
2. 调试扩展本身

**别在无人看管的时候开 open。**

## 一个已知的设计取舍

`script_run` 在 whitelist 模式下，`args` 用的是配置里写死的值。这意味着同一个脚本不能带不同参数跑两次（除非配两个 alias）。

这是故意做的：参数可变就等于把命令行的一部分交给了模型。

如果确实需要动态参数，给那个脚本加一个「只接受固定枚举值」的包装脚本，而不是放开参数。

## 上报安全问题的建议做法

如果你发现这个扩展有绕过限制的方式，请开 issue 说明复现步骤。不要把利用代码直接贴出来。
